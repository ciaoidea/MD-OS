# Interactive Executive Runtime Model

MD-OS requires two separate operating entrypoints with different ownership of
the interaction loop.

```text
development entrypoint
  human -> Codex -> MD-OS

controlled operating entrypoint
  human / agent / sensor -> MD-OS -> native router / Codex -> gate -> executor -> sensor -> verifier
```

The existing `bootstrap-md-os-codex.sh` remains the verified development path.
It is not replaced or invoked by the controlled operating entrypoint.

The controlled entrypoint is the **Interactive Executive Runtime**. Its first
human interface is the **MD-OS Control Console**.

## Core Inversion

Today, the development launcher lets Codex operate MD-OS by reading and
applying the Operating Filesystem. The Interactive Executive Runtime inverts
that relationship:

```text
Codex development mode
  Codex owns the turn and operates MD-OS.

MD-OS Control Console mode
  MD-OS owns the turn and invokes Codex as a bounded reasoning component.
```

This is an additional operating mode, not a migration that removes the Codex
development launcher.

## One Interface, Several Input Sources

There is not one GUI for Markdown and another for JSON. The Control Console is
one interface over several degrees of semantic constraint.

Every source enters through an `InputEvent`:

```text
human  -> authority: operator
agent  -> authority: advisory
sensor -> authority: evidentiary
```

Source type does not grant execution authority. In the initial runtime only a
human operator can approve an action proposal. An agent may propose and a
sensor may report evidence, but neither may cross the human commitment gate.

## Six Canonical Categories

The runtime preserves six categories:

```text
Markdown  -> method and semantic links
JSON      -> contracts and state
NDJSON    -> event history
Executors -> real action
Sensors   -> observed effect
Verifiers -> evidence-grounded outcome status
```

The Control Console makes their transitions visible. It does not collapse
executor completion, observed effect, and verified outcome into one status.

## Initial Closed Loop

The first implementation has two explicit input lanes. A human-entered command
already covered by the deterministic native policy does not require semantic
translation:

```text
exact human command (`ls`, `pwd`, `cd`, ...)
-> direct argv parser
-> native read-only policy
-> bounded executor inside `md-os/`
-> captured output
-> receipt and event readback
```

The native lane deliberately bypasses Codex. It never invokes a shell
interpreter, expands a pipeline, evaluates a substitution, or accepts an
unbounded filesystem path. The human command is the intent and the checked-in
policy is its preauthorization gate. Advisory agents and sensor inputs cannot
use this lane.

Everything else follows the typed cognitive lane:

```text
InputEvent
-> ephemeral read-only `codex exec`
-> schema-valid ProposalSpec
-> action registry resolution
-> explicit human decision
-> registered module command, when approved
-> executor readback
-> truthful `unverified` or `failed` verdict
```

Important properties:

- Exact preauthorized native commands bypass Codex and execute immediately.
- The native command catalogue and argument rules are explicit in
  `md-os/kernel/interaction/native_command_policy.json`.
- Filesystem-native commands start at `md-os/`; `cd` cannot cross that
  boundary.
- Native commands use direct argument vectors, not Bash evaluation, pipes,
  redirection, command substitution, or arbitrary generated shell text.
- Codex receives a read-only sandbox.
- The Codex session is ephemeral by default.
- Codex output must match `interactive_proposal.schema.json`.
- Cross-field lane and action rules are revalidated by deterministic MD-OS
  code because the Codex Structured Outputs schema supports a constrained
  JSON Schema subset.
- Native shell text generated by Codex is never an executable interface.
- Every model-proposed action stops at a human gate.
- Only commands already represented in the MD-OS module registry can run.
- Approval is single-use.
- Successful executor completion remains `unverified` until a
  connector-specific sensor and verifier prove the requested effect.
- The HTTP console binds only to `127.0.0.1` and uses a per-process mutation
  token.
- Human natural-language commands are appended to private host-local
  `md-os/ops/local/control-console/history.ndjson` by default, as the MD-OS
  equivalent of shell command history.
- Full input/response transcripts are not persisted by default. They require
  the explicit `--save-chat` option and remain host-local and ignored by Git.
- Command history and session history are context, not canonical memory. Their
  contents require explicit verified promotion before they may affect stable
  MD-OS state.

## Relationship To The Former Cortex Prototype

The former Cortex prototype demonstrated two important control shapes:

```text
valid native command -> direct host execution without the model
natural language -> AI -> tagged output -> validator -> native executor
```

Its repository name described the whole cortex while its implementation was
primarily a semantic output gateway and action dispatcher. MD-OS preserves the
useful direct-command bypass while replacing AI-generated free native-command
output with typed proposals and registered execution routes:

```text
former prototype
  human `ls` -> host shell directly
  AI -> `AGENT: os` -> arbitrary native command

MD-OS Control Console
  human `ls` -> deterministic native policy -> bounded executor
  AI -> ProposalSpec -> registry gate -> declared executor
```

The continuity with Cortex is the dual shell: machine syntax should not waste a
model turn, while human language may use a model. The architectural correction
is that direct native execution is now a declared, bounded policy lane rather
than arbitrary shell authority.

## Multiple Context Windows

Multiple AI context windows are not a novel mechanism. They are multiple
Codex sessions or app-server threads. The architectural rule is that MD-OS,
not a parent model, must own their process graph.

Possible future composition:

```text
MD-OS runtime
├── planner session  -> PlanSpec
├── critic session   -> CritiqueSpec
├── proposer session -> ActionSpec
└── verifier session -> VerificationReport
```

No session should recursively create an unbounded tree of sessions. A future
scheduler must declare:

```text
role registry
dependency graph
maximum depth
maximum concurrent sessions
token and wall-time budget
allowed input artifacts
required output schema
tool and permission profile
stop condition
verifier
```

The first implementation starts one ephemeral Codex proposal session per
human turn. Multi-session scheduling is outside its current claim.

## Non-Novelty And Contribution Boundary

Launching multiple model sessions, validating structured output, requesting
approval, and building a local GUI are established techniques. The current
work does not claim to invent them.

The engineering contribution under test is their coherent integration with
Operational Context as Filesystem:

```text
MD-OS owns the process graph;
models produce typed proposals;
verified artifacts connect bounded processes;
authority remains explicit;
action, observation, verification, and memory remain separate.
```

Whether that integration improves agent reliability, cost, or continuity
relative to simpler orchestration remains an empirical question.

## Current Claim

The current prototype may claim:

> MD-OS can receive a typed input event, invoke Codex in an ephemeral read-only
> mode when semantic interpretation is required, or bypass Codex for an exact
> preauthorized read-only native command; it validates model proposals,
> prevents their automatic execution, requires a human decision, and routes an
> approved proposal only through the registered module runtime.

It may not yet claim:

- cloud agent teams;
- autonomous recursive delegation;
- persistent multi-thread Codex orchestration;
- complete sensor coverage;
- independently verified effects for every connector;
- adversarial containment of a compromised host process;
- production maturity.
